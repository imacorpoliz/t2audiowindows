# RE: протокол AppleAudio ↔ T2 и роль AppleUSBVHCI (R4, R5, R7 частично, R9)

Статический анализ, 2026-10-28, `objdump -d -M intel` + разбор импортов. Бинарники те же, что в [`START_IO_BSOD_ROOT_CAUSE.md`](START_IO_BSOD_ROOT_CAUSE.md). VA при ImageBase `0x140000000`. Метки: **доказано** (инструкции), **вероятно**, **гипотеза**.

## 1. AppleUSBVHCI сам ведёт handshake с bridgeOS — **доказано**

| VA | Что |
|---|---|
| `0x140002690` | `NOTIFICATION_ALIVE`: tag 1, type 3, device_id 0, `msg 0x64` (100), payload `proto_ver = 1`, `msg_ver = 3`, длина `0x1D`. Ждёт событие `0x27448` 5 с, ответ должен иметь `msg 0x64` |
| `0x140002864` | `SET_REMOTE_ACCESS`: tag 2, type 1, device_id 0, `msg 0x20` (32), payload `mode` = второй аргумент, длина `0x1D`. Ответ должен иметь `msg 0x21` и `status 0` |
| `0x1400020F2` → `0x140002101` | при инициализации: ALIVE, затем `SET_REMOTE_ACCESS(r14)`, где `r14d = 1` (`0x140001F68`) |
| `0x140016EA0` → `0x140016EB1` | после `KeDelayExecutionThread(100 мс)` (вероятно, возврат из сна): ALIVE, затем `SET_REMOTE_ACCESS(1)` |
| `0x140016F8F`–`0x140016FAA` | обработчик смены состояния питания (состояния 5–6): `SET_REMOTE_ACCESS(0)` |

Выводы:
* На Windows remote access включает **AppleUSBVHCI с `mode = 1`**, а не 2, как в kaiT2en на Linux.
* **AppleAudio.sys никогда не отправляет `SET_REMOTE_ACCESS` и `NOTIFICATION_ALIVE`** (см. §2).
* Следствие для T2AudioPort (исправлено в коде): драйвер больше не отправляет `SET_REMOTE_ACCESS(2)` на стадии 4 и `OFF` при остановке/удалении устройства. `OFF` от аудиодрайвера оставил бы T2 выключенным до следующей инициализации VHCI, а AppleAudio — без звука после отката. `T2AudioStartIo` больше не требует remote access.

## 2. Всё, что AppleAudio отправляет в T2 (R5) — **доказано**

Все 30 вызовов функции отправки `0x140004A4C` (`IOCTL 0x222018`). Тип сообщения (`+4`) везде 1 (COMMAND), тег — счётчик контекста (`mov eax,[rcx]; inc; mov [rcx],eax`, затем `% 0x7F + 1` внутри `0x140004A4C`).

| Функция | msg | Длина | Назначение |
|---|---|---|---|
| `0x1400027D0` | 101 `GET_DEVICE_LIST` | 0x15 | список устройств |
| `0x1400029D4` | 24 `GET_INPUT_STREAM_LIST` | 0x15 | входные потоки |
| `0x140002B40` | 26 `GET_OUTPUT_STREAM_LIST` | 0x15 | выходные потоки |
| 21 функция `0x140002C94`…`0x140004054` | 7 `GET_PROPERTY` | 0x31 | см. таблицу ниже; ответ: `msg == 8`, `status == 0`, значение с `+0x31` |
| `0x14000251C` | **28** (нет в kaiT2en) | 0x15 | список элементов управления (controls), см. §8 |
| `0x1400042C4` | 11 `PROPERTY_LISTENER` | 0x29 | подписка на изменения (jack) |
| `0x1400044E4` | 18 `SET_INPUT_STREAM_ADDRESS_RANGES` | — | регистрация буфера записи (микрофон) |
| `0x1400045FC` | 9 `SET_PROPERTY` | 0x42 | **только `'nsrt'`** (номинальная частота): значение — double из `cvtsi2sd` (`0x140004672`); ответ `msg 10` |
| `0x1400048B0` | 0 `START_IO` | 0x15 | ответ `msg 1` |
| `0x140004970` | 2 `STOP_IO` | 0x15 | ответ `msg 3` |

Свойства `GET_PROPERTY` (element = 0 у всех; адреса — константы в `.rdata`, например `0x14000EC98`/`0x14000ECA0`):

| scope | selectors |
|---|---|
| `'glob'` | `'uid '`, `'lnam'`, `'clas'`, `'bcls'`, `'bcvl'`, `'scci'`, `'lcdr'`, `'lcdv'`, `'nsr#'`, `'nsrt'`, `'ring'`, `'pfta'`, `'sact'`, `'term'`, `'ltnc'` |
| `'outp'` | `'jack'`, `'ltnc'`, `'saft'` |
| `'inpt'` | `'jack'`, `'ltnc'`, `'saft'` |

Заметно: AppleAudio читает `'pfta'` (список **доступных** физических форматов), а не `'pft '`, плюс `'nsrt'`/`'nsr#'` (частота и число доступных частот) и `'ring'` (**вероятно**, размер кольца). Формат он не переключает: единственный `SET_PROPERTY` — частота.

Сравнение с T2AudioPort:

| Шаг | AppleAudio | T2AudioPort |
|---|---|---|
| ALIVE / SET_REMOTE_ACCESS | не шлёт (делает VHCI) | **больше не шлёт** (исправлено) |
| GET_DEVICE_LIST, `'uid '` | да | да |
| GET_OUTPUT_STREAM_LIST | да | да |
| формат | `'pfta'` + `SET_PROPERTY 'nsrt'` | `'pft '` (текущий формат), частоту не задаёт |
| латентность | `'ltnc'`, `'saft'` | да |
| START_IO / STOP_IO | да | да |

Открыто: нужен ли `SET_PROPERTY 'nsrt' = 48000` перед первым `START_IO`. Если T2 уже на 48 кГц (это показывает `'pft '` из NOTES.md), то, **вероятно**, нет.

## 3. Формат сэмплов в кольце (R7, частично) — **доказано**

`0x14000B04E`–`0x14000B078` (один из вариантов цикла копирования):

```
movsx  r8d, WORD PTR [rdi] / [rdi+2]   ; 16-битный сэмпл L / R из буфера Windows
mov    rax, [rsi+0x158]                ; WAVEFORMATEX потока
movzx  edx, WORD PTR [rax+0xe]         ; wBitsPerSample (16)
mov    rax, [rsi+0xa30]
mov    ecx, [rax+0x71d8]               ; разрядность канала устройства (24)
sub    ecx, edx                        ; 24 - 16 = 8
shl    r8d, cl                         ; сэмпл << 8
mov    [r15], r8d                      ; 32-битная запись в кольцо
```

24 значащих бита в **младших** байтах 32-битного контейнера (S24_LE) — та же раскладка, что получает наш драйвер сдвигом `>> 8` 32-битного сэмпла Windows.

Попутно: перед записью AppleAudio обрабатывает сэмплы на CPU — double, деление на полную шкалу, ограничение (`minsd`/`comisd`), вызовы `0x14000779C`, `0x140007454`, `0x14000A19C`. Набор фильтров выбирается по глобальной `0x140014688` (значения 6 и 10 — **вероятно**, модель Mac). Маска отключения каналов — `0x14001468C`. **Вероятно**, это эквализация по динамикам, которую на macOS делает CoreAudio DSP: на Windows она живёт в AppleAudio, а не в прошивке T2. Наш драйвер её не делает, поэтому твитеры получат полный диапазон. Первые пробы — только на малой громкости.

Не разобрано: раскладка стерео → 6 каналов динамиков и сами коэффициенты фильтров. Показанный цикл пишет 2 канала (`ebx` 0..1), а 6-канальный вариант нужно искать среди соседних веток `0x14000A715`–`0x14000B2C0`.

## 4. `PROPERTY_CHANGED` и jack (R4) — **доказано**, раскладка — **вероятно**

Обработчик `0x222020` в AppleAudio (`0x1400012C7`–`0x140001332`):
* `scope = *(u32*)(buf+0x21)`: `'outp'` → флаг `[g+0x38] = !флаг`, затем вызов `[g+0x08]([g+0x10])` через CFG; `'inpt'` → `[g+0x39]`, `[g+0x18]([g+0x20])`. `g = [0x140014690]`.
* Значение свойства из сообщения **не читается**: состояние jack просто переключается на каждое уведомление. Актуальное значение AppleAudio получает отдельным `GET_PROPERTY 'jack'` (`0x140003224` для `'inpt'`, `0x14000330C` для `'outp'`).
* Раскладка (по kaiT2en `t2audio_msg_read_property_changed`): `+0x15 obj (u64)`, `+0x1D element`, `+0x21 scope`, `+0x25 selector`. Смещение scope `+0x21` совпадает — **вероятно**, верно и остальное.

## 5. Выбор получателя `0x222020` (R9) — **доказано**

`0x140002461`–`0x140002477`: `IoGetDeviceInterfaces(&KSCATEGORY_AUDIO, NULL, 0, &list)`. Флаги = 0 — только **включённые** интерфейсы. Функция `0x1400023F0` выполняется заново **на каждое сообщение** (без кэширования) в worker thread: её ставит в очередь `0x140002274` (`lea rax, 0x1400023F0` по адресу `0x1400022DD`). Значит, наш обработчик вызывается на `PASSIVE_LEVEL`, и одновременно установлен только один из драйверов (наш или AppleAudio), так что неоднозначности с выбором получателя нет.

## 6. Классификация входящих сообщений в AppleUSBVHCI — **доказано**

`0x140001D72`–`0x140001DFB`:

| type | msg | Действие VHCI |
|---|---|---|
| 1 (COMMAND) | 4 `UPDATE_TIMESTAMP` | доставка через `0x222020`, затем сам отвечает `UPDATE_TIMESTAMP_RESPONSE` (34) |
| 1 | другие | отбрасывается |
| 2 (RESPONSE) | любой | `KeSetEvent(0x27448)` — будит ожидающий `0x222018` |
| 3 (NOTIFICATION) | 100 `ALIVE` | тоже `KeSetEvent(0x27448)` (как ответ!) |
| 3 | другие (`PROPERTY_CHANGED` и т.п.) | доставка через `0x222020` |

Поэтому T2AudioPort теперь проверяет, что тег ответа совпадает с тегом запроса: ALIVE, пришедший во время нашего запроса, не будет принят за ответ.

## 7. Питание (R8) — **доказано**

`PcRegisterAdapterPowerManagement` (`0x14001663F`) регистрирует объект с vtable `0x14000EBD8`: `PowerChangeState` = `0x140001520`, `QueryPowerChangeState` = `0x140001610`, `QueryDeviceCapabilities` = `0x1400015D0` (возвращает 0). Оба метода сначала передают вызов дочерним объектам (`[node+0x228]`, слот `+0x18`), затем:

| Событие | VA | Действие |
|---|---|---|
| `QueryPowerChangeState(D3)` | `0x140001667` → `0x1400041EC` | флаг «нужна переинициализация» `[g+0x3A] = 1`; **STOP_IO** каждому устройству с активным I/O (`[dev+0xE998]`), счётчик меток `[dev+0xE99C] = 0` |
| `PowerChangeState(D1…D3)` | `0x140001570` → `0x140004250` | то же STOP_IO (если ещё не остановлено), без флага |
| `PowerChangeState(D0)` при флаге | `0x14000158E` → `0x140004BA0` | `KeDelayExecutionThread(1 с)`, затем `0x140004398`: для каждого **входного** потока заново пишет диапазоны своих буферов в таблицу буферов T2 (`0x1400046F8`: сигнатура `0x19870423`, версия ≥ 2, записи по UID с шагом `0xBDEC`) и шлёт `SET_INPUT_STREAM_ADDRESS_RANGES` (msg 18); флаг сбрасывается |

Чего **нет**: записи sleep marker `0x19770525` (константы нет в бинарнике), `SET_REMOTE_ACCESS` (его ведёт VHCI, §1), повторного чтения описания выходного кольца. Кольцо динамиков после сна, видимо, остаётся тем же; START_IO снова приходит из `SetState(RUN)`, когда аудиодвижок перезапускает поток.

Для T2AudioPort **сделано** (`src/Power.c`, не проверено на железе): статический `IAdapterPowerManagement` регистрируется в `T2AudioStartDevice`.
* STOP_IO в `QueryPowerChangeState(D3)` (пока VHCI ещё жив) и в `PowerChangeState(D1…D3)`.
* В D1–D3 копирование не пишет в BAR0 (`PoweredDown`).
* На D0 START_IO не повторяется — как у AppleAudio, он приходит из следующего `SetState(RUN)`.
* Флаг `HardwareIoActive` (interlocked) гарантирует один STOP_IO на один START_IO при любом порядке «поток выходит из RUN / питание».

Открыто: если аудиодвижок оставит поток в RUN на всё время сна, после пробуждения будет тишина до следующего перезапуска потока.

Попутно: `0x1400046F8` показывает, что для **входа** (микрофон) AppleAudio сам выделяет буферы и вписывает их адреса в общую таблицу. Выход (динамики) использует кольцо, которое предоставляет T2 (BAR), как у нас.

## 8. msg 28 — список элементов управления — **доказано** (назначение — **вероятно**)

`0x14000251C`: COMMAND msg 28 (`0x1C`) на `device_id`, длина `0x15`. Ответ должен иметь `msg 29` (`0x1D`) и `status 0`. Дальше:

* `u64` по `+0x15` — число объектов (сохраняется в `[dev+0xE178]`);
* с `+0x1D` — массив `u64` идентификаторов объектов.

Для каждого объекта вызываются два `GET_PROPERTY` (`0x140002E6C`, `0x140002C94`), и полученный класс сравнивается с `'levl'` (уровень/громкость), `'slct'` (селектор) и `'togl'` (переключатель). Для каждого класса свой набор чтений (`0x140003138`/`0x140003044`, `0x140002F58`, `0x140002D80`), затем проверяется подкласс `'jack'`. Это аналог `GET_OUTPUT_STREAM_LIST`, но для controls (громкость, mute, выбор выхода, детектор наушников).

Для вывода на динамики это **не нужно**: kaiT2en звучит без msg 28, громкость в Windows можно делать программно (в аудиодвижке). Пригодится позже для аппаратной громкости и детектора наушников.
