# RE_tag_semantics: Семантика поля tag в сообщениях BCE (Задача R2)

> **Дата анализа:** 28 октября 2026 г.  
> **Инструменты:** Дизассемблер Capstone, Python PE parser, анализ бинарников `AppleAudio.sys` (SHA256 `cd8b81fabc9b…a150`) и `AppleUSBVHCI.sys` 6.1.7500.5 (SHA256 `0438292090fc…55c1`).  
> **Статус выводов:** **ДОКАЗАНО** (с указанием точных инструкций и адресов VA/RVA; гипотезы о поведении bridgeOS явно помечены).

---

## 1. Как поле tag формируется в `AppleAudio.sys`

В `AppleAudio.sys` отправка всех команд через `IOCTL 0x222018` выполняется функцией `FUN_140004a4c`.  
Непосредственно перед заполнением параметров `IoBuildDeviceIoControlRequest` драйвер обновляет первые 4 байта сообщения (`tag`):

```assembly
; AppleAudio.sys VA: 0x140004AB9 - 0x140004AD9 (RVA 0x4AB9 - 0x4AD9)
0x140004ab9: mov  ecx, dword ptr [rdi]        ; rdi указывает на буфер сообщения (tag по смещению 0)
0x140004abb: mov  eax, 0x02040811             ; Магическая константа деления на 0x7F (127)
0x140004ac0: mul  ecx                         ; edx:eax = ecx * 0x02040811
0x140004ac2: mov  eax, ecx
0x140004ac4: xor  r8d, r8d
0x140004ac7: sub  eax, edx
0x140004ac9: shr  eax, 1
0x140004acb: add  eax, edx
0x140004acd: xor  edx, edx
0x140004acf: shr  eax, 6                      ; eax = ecx / 0x7F
0x140004ad2: imul eax, eax, 0x7f             ; eax = (ecx / 0x7F) * 0x7F
0x140004ad5: sub  ecx, eax                    ; ecx = ecx % 0x7F (остаток от 0 до 126)
0x140004ad7: inc  ecx                         ; ecx = (ecx % 0x7F) + 1 (результат от 1 до 127)
0x140004ad9: mov  dword ptr [rdi], ecx        ; Запись нового tag обратно в буфер сообщения
```

### Доказанный факт:
1. `AppleAudio.sys` использует **строго циклический счетчик в диапазоне от 1 до 127** (`1 <= tag <= 127`, `0x01..0x7F`).
2. Тег никогда не равен `0`.
3. Тег не является ASCII-строкой.

## 2. Как `AppleUSBVHCI.sys` обрабатывает `IOCTL 0x222018`

Таблица диспетчеризации IOCTL в `AppleUSBVHCI.sys` находится в функции `0x140017C50`:
```assembly
; AppleUSBVHCI.sys VA: 0x140017D1D - 0x140017D56
0x140017D1D: sub  ecx, 0x222000
...
0x140017D54: cmp  ecx, 4                      ; Проверка: code == 0x222018
0x140017D56: jne  0x17FD7
```

При обращении к `0x222018` управление передается в функцию `0x140002128`:
1. **Передача сообщения в bridgeOS (`0x1400021B4`):**
   * Вызывается `0x1400027C4(ctx, InputBuffer, InputBufferLength)`.
   * `AppleUSBVHCI.sys` **не валидирует и не модифицирует поле `tag`** — буфер передается в bridgeOS как есть.
2. **Синхронное ожидание (`0x1400021E3`):**
   * `KeWaitForSingleObject` ожидает сигнальное состояние статического события по адресу `RVA 0x27448` с таймаутом 5 секунд (`-50 000 000` в единицах 100 нс).
3. **Получение ответа (`0x14000222A`):**
   * Ответный буфер bridgeOS берется из глобального указателя `RVA 0x27440` и копируется в `OutputBuffer` вызывающего потока (`0x140002235: call memcpy`).
   * В поле `IoStatusBlock.Information` записывается длина скопированного ответа (`0x140002240: mov qword ptr [rsi], rdx`).
4. **Проверка в `AppleAudio.sys` (`0x140004B5D`):**
   * `AppleAudio.sys` проверяет: `if (IoStatus.Information == 0) return STATUS_UNSUCCESSFUL (0xC0000001)`.

## 3. Типы сообщений протокола и их диспетчеризация в `AppleUSBVHCI.sys`

По протоколу BCE определены три типа сообщений (`header.type` по смещению `+4`):
* **`type == 1`**: COMMAND (команда от bridgeOS к хосту)
* **`type == 2`**: RESPONSE (ответ на ранее отправленную хостом команду)
* **`type == 3`**: NOTIFICATION (асинхронное уведомление от bridgeOS)

В диспетчере входящих сообщений bridgeOS (`AppleUSBVHCI.sys` `0x140001CF0`–`0x140001DEF`):
```assembly
; AppleUSBVHCI.sys VA: 0x140001D72 - 0x140001DEF
0x140001D72: movzx ecx, byte ptr [rbx + 4]    ; rbx = буфер пакета, +4 = header.type
0x140001D76: sub   ecx, 1                     ; type == 1 (COMMAND)?
0x140001D79: je    0x1DA4                     ; переход к проверке msg == 4
0x140001D7B: sub   ecx, 1                     ; type == 2 (RESPONSE)?
0x140001D7E: je    0x1DEF                     ; переход к KeSetEvent(0x27448)!
0x140001D80: sub   ecx, 1                     ; type == 3 (NOTIFICATION)?
0x140001D83: jne   0x1E05
0x140001D85: cmp   dword ptr [rbx + 0xd], 100 ; msg == 100 (NOTIFICATION_ALIVE)?
0x140001D89: je    0x1DEF                     ; ALIVE -> тоже KeSetEvent(0x27448)!
0x140001D8B: jmp   0x1DAA                     ; остальные type 3 -> доставка через 0x222020 (0x140002274)
...
0x140001DA4: cmp   dword ptr [rbx + 0xd], 4   ; для type 1: msg == 4 (UPDATE_TIMESTAMP)?
0x140001DA8: jne   0x1D9A                     ; если нет -> ОТБРАСЫВАЕТСЯ
0x140001DAA: call  0x140002274                ; доставка в аудиодрайвер через 0x222020!
...
0x140001DEF: lea   rcx, [rip + 0x2564f]       ; RVA 0x27448 (событие ожидания ответа)
0x140001DF6: xor   edx, edx
0x140001DF8: xor   r8d, r8d
0x140001DFB: call  KeSetEvent                 ; Пробуждение потока, вызвавшего 0x222018
```

### Доказанные факты диспетчеризации:
1. `type == 1` (COMMAND) доставляется в аудиодрайвер через `0x222020` **только при `msg == 4`** (`UPDATE_TIMESTAMP`). Все остальные `type == 1` отбрасываются.
2. `type == 2` (RESPONSE) **никогда не уходит в `0x222020`**; оно всегда будит `KeSetEvent(0x27448)`.
3. `type == 3` (NOTIFICATION) доставляется через `0x222020` для всех сообщений, **кроме `msg == 100`** (`NOTIFICATION_ALIVE`).
4. **Критический риск: `NOTIFICATION_ALIVE (100)`** не передается в аудиодрайвер, а вместо этого переходит на `0x140001DEF` и взводит то же самое событие `KeSetEvent(0x27448)`, что и ответ на команду! Если `NOTIFICATION_ALIVE` поступит в момент, когда наш поток ожидает ответ на `0x222018`, событие сработает досрочно, и вызывающий поток получит в выходной буфер пакет ALIVE вместо настоящего ответа на команду.

## 4. Семантика поля tag и риски

* `AppleUSBVHCI.sys` **не проверяет поле `tag`** в ответах. Вся обработка `IOCTL 0x222018` однопоточна и опирается на статическое событие `0x27448`.
* **Поведение bridgeOS в отношении `tag`:**
  - *Гипотеза:* bridgeOS зеркалит полученный `tag` в заголовке ответа `type == 2`.
  - *Гипотеза:* диапазон 1..127 в драйвере Apple обусловлен 7-битным идентификатором транзакции в таблицах IPC bridgeOS.
* **Необходимость проверки тега в драйвере:**
  Поскольку `NOTIFICATION_ALIVE` может преждевременно разбудить `0x222018`, аудиодрайвер обязан проверять, что пришедший ответ содержит `header.type == 2` и `tag == ожидаемый_тег`. Если тег не совпадает, драйвер должен отвергать ответ (в текущем коде `T2AudioSendBceMessage` это уже учтено).

| Параметр | Значение | Статус |
| :--- | :--- | :--- |
| Правильный формат `tag` | Число 1..127 (`(*tag % 0x7F) + 1`), инкрементируемое на каждый запрос | **ДОКАЗАНО** |
| Фильтрует ли `AppleUSBVHCI` по тегу? | Нет, `AppleUSBVHCI` проверяет только `header.type` и пробуждает поток | **ДОКАЗАНО** |
| Уходят ли ответы с чужим тегом в `0x222020`? | Нет, `type == 2` всегда идет в `KeSetEvent`, а в `0x222020` идут `type == 1 (msg 4)` и `type == 3 (кроме msg 100)` | **ДОКАЗАНО** |
| Поведение при `NOTIFICATION_ALIVE` | Будит `KeSetEvent(0x27448)` — создает риск подмены ожидаемого ответа | **ДОКАЗАНО** |
| Действие для `T2AudioPort` | Проверять `tag` и `type == 2` при возврате из `0x222018`, таймаут ожидания драйвера > 5 с (VHCI таймаут 5 с) | **РЕАЛИЗОВАНО** (в коде `diagnostics`) |
